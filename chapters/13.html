CHAPTER 13 / LINUX 0.11

物理内存：mem_map 如何分配、共享和回收页面

从 BIOS 扩展内存值到 LOW_MEM=1MiB 的管理边界，逐条追踪 mem_init、get_free_page、free_page 的字节计数与错误处理。

LOW_MEM · 4KiB · 引用计数

一张“空闲表”，为什么不能只有 0 和 1？

假设两个进程都映射同一物理页，父进程退出时是否能立即把这页还给分配器？不能，因为子进程仍在使用它。于是 Linux 0.11 的 mem_map 不是“每页一个 bit”的位图，而是每个受管理页框对应一个 unsigned char，用于记录共享计数或保留状态。

内核必须回答三个问题：哪些物理地址参与页分配？如何找到空闲的 4KiB 页并清零？多个用户共享时，释放一次应该怎样修改状态？这章从数值边界开始，不会把虚拟地址和物理地址混为一谈。

LOW_MEM=0x100000：原稿中的 256KiB 是错误的

mm/memory.c 中明确写出 LOW_MEM = 0x100000（1MiB）、PAGING_MEMORY = 15*1024*1024、PAGING_PAGES = PAGING_MEMORY >> 12，因此数组最多对应 3840 个 4KiB 页，覆盖物理地址 [1MiB,16MiB) 的范围。MAP_NR(addr) 将物理地址减去 LOW_MEM 后右移 12 位，得到从 0 开始的数组下标。

v0.11 mm/memory.c 中的真实定义
#define LOW_MEM 0x100000
#define PAGING_MEMORY (15*1024*1024)
#define PAGING_PAGES (PAGING_MEMORY>>12)
#define MAP_NR(addr) (((addr)-LOW_MEM)>>12)
#define USED 100

前 1MiB 中包含 BIOS/设备保留区、早期内核映射和缓冲区等，但不能写成固定几个奇怪的 36KiB/148KiB 分区并假设所有机器相同。Linux 0.11 的低端内存管理与现代 PC 的 e820、NUMA 或高端内存模型并不是同一机制。

物理地址 0x200000 对应 mem_map 的第几项？（展开核对）

(0x200000-0x100000)>>12 = 0x100000 / 4096 = 256。下标 256 对应物理 2MiB 的起始页框。

从 BIOS 报告到主内存起始位置

setup.s 用 BIOS INT 15h,AH=0x88 获取扩展内存大小并写入 0x90002；main.c 用 EXT_MEM_K 读取，计算 1MiB 加扩展大小、按 4KiB 对齐、把可使用上限限制在 16MiB。然后根据总内存量选择 1、2 或 4MiB 的 buffer_memory_end，并考虑可选的 RAMDISK 占用，确定 main_memory_start。

这意味着不能宣称“1MiB–16MiB 全部立即分配给普通页”：它只是 mem_map 的数组覆盖范围，真正能分配的页从 main_memory_start 开始、直到 HIGH_MEMORY，其余对应项仍被标记成不可用。

边界计算（教学伪代码）
detected = align_down(0x100000 + EXT_MEM_K*1024, 4096)
HIGH_MEMORY = min(detected, 0x1000000)
main_memory_start = buffer_memory_end
if RAMDISK:
    main_memory_start += rd_init(main_memory_start, RAMDISK*1024)
mem_init(main_memory_start, HIGH_MEMORY)

原始源码中的 HIGH_MEMORY 由 mem_init 赋值；该教程只讨论 0.11 的 16MiB 上限，不能把它解释成 386 处理器所有寻址能力的上限。

mem_init 不是 memset 全 0

调用 mem_init(start_mem,end_mem) 后，先令 HIGH_MEMORY=end_mem，再把整个 mem_map 数组填为 USED=100。接下来计算 i=MAP_NR(start_mem)，以页为单位逐项将 [start_mem,end_mem) 对应的元素置 0。

v0.11 的 mem_init 核心循环（节选）
for (i=0 ; i<PAGING_PAGES ; i++)
    mem_map[i] = USED;
i = MAP_NR(start_mem);
end_mem -= start_mem;
end_mem >>= 12;
while (end_mem-->0)
    mem_map[i++]=0;

因此每个字节的语义至少有：0 表示目前可以分配；1 表示被分配且一份引用；2 及以上表示存在多个引用；USED=100 是初始化保留标记，而非真实有 100 个使用者。不要把它当作 struct page、Buddy 或 SLUB。

get_free_page 的逆向扫描与清零

get_free_page 用老式 x86 内联汇编完成选择：从 mem_map 末端反向扫描找一个值为 0 的字节；命中后把该元素标为 1，把索引转换成物理页起始地址，并使用 rep stosl 将整页 4096 字节写成 0。若没有空闲项则返回物理地址 0 作为失败标志。

这里使用的 std; repne; scasb 表示向低地址搜索；由于方向标志此前由 std 设为倒序，源码从页面末尾附近的地址向低地址执行 rep stosl，恰好把 4KiB 全部写为零。图解如果把“从前往后找到第一个空页”作为确定事实，会颠倒物理页选择顺序。

get_free_page 的功能等价示例（不是汇编逐字翻译）
for i in reversed(range(PAGING_PAGES)):
    if mem_map[i] == 0:
        mem_map[i] = 1
        page = LOW_MEM + i * 4096
        zero_fill(page, 4096)
        return page
return 0

这项调用同时承担页资源登记与数据清零：不清零可能让不同进程之间的数据残留暴露给新用户。源码的页清零细节是安全与正确性的一部分。

free_page 怎样避免释放仍被共享的页面

free_page(addr) 对小于 LOW_MEM 的地址直接返回；如果超出 HIGH_MEMORY 则 panic。对于受管理页，它通过 (addr-LOW_MEM)>>12 找到引用计数并递减。递减前非零时返回：从 2 到 1 仍是引用页，从 1 到 0 才空闲。若试图释放本来就是 0 的页，则触发 panic("trying to free free page")。

数值自检：引用计数转移
# 假设映射页物理引用计数为 2
count = 2
count -= 1   # 父进程不再引用
assert count == 1
count -= 1   # 子进程不再引用
assert count == 0

这里还需要注意后续的 copy_page_tables 和 un_wp_page 会改变 mem_map；如果把 fork/COW 算作“内存复制”而漏记这份共享引用，退出路径可能在另一任务仍可访问时回收物理页。

为什么 mem_map=100 不是‘100 个共享进程’？（展开核对）

USED 是初始化保留区域时的哨兵值。它用来阻止页分配器把该页当作空闲页；并不代表存在 100 个有效映射。

复核地址、计数与分配方向

只读源码练习
grep -n 'LOW_MEM\|PAGING_PAGES\|MAP_NR\|USED' mm/memory.c
grep -n 'get_free_page\|free_page(unsigned\|mem_init' mm/memory.c
grep -n 'HIGH_MEMORY\|main_memory_start\|buffer_memory_end' init/main.c

预期能找到 LOW_MEM=1MiB、3840 个候选页、USED=100、逆向扫描、清零和内存上限选择。查找实际函数名后再看源码，不应凭假想的 C 循环把内联汇编改写成“原始代码”。本例可在任何现代机器上检查公式，但不是 0.11 的物理页分配性能基准。

直接证据与后续问题

  1. mm/memory.c：PAGING_PAGES、mem_map、get_free_page、free_page、mem_init。
  2. init/main.c：扩展内存与缓冲区边界。
  3. boot/setup.s：BIOS 扩展内存信息来源。
  4. kernel/fork.c：copy_mem 与进程共享页表的入口。
